# 既存Skill・指示の移行

既存のSkillや開発指示をAACLへ移すときは、ファイル名だけで統合せず、本文の責務、手順、参照関係を確認してからAssetを作成します。元ファイルとRuntime設定は、AACL側の登録内容と接続を確認するまで保持します。

## 移行前に整理する

1. 移行元のファイルと読み込み設定を一覧にし、元の状態を復元できるようコピーを保管する。
2. 同じ名前のSkillが複数ある場合は本文を比較する。Runtime固有の記法やパスの違いと、責務・手順・判断基準の違いを分けて確認し、統合方針を決める。
3. Workflow、Role、Skill、Ruleのどの種類で管理するかを、内容と役割から決める。

## 内容をAssetへ対応づける

| 内容 | AACLでの管理 |
| --- | --- |
| 工程、許可する遷移、完了条件 | Workflow |
| 工程を担当する責務と成果 | Role。Workflowの各工程へ紐づける |
| 再利用する手順や知識 | Skill |
| 共通して適用する制約や判断基準 | Rule |
| Skillが読む資料やスクリプト | Skillの補助ファイル |

Workflow内の単一工程を担当する指示は、SkillではなくRoleとして登録し、そのWorkflowの工程へ割り当てます。画面では既存Assetの種類を切り替えられないため、種類が異なる場合は正しい種類でAssetを作成し、必要な紐づけを付け替えます。

Skill本文にはそのSkill自身の手順を保存します。別のSkill本文を補助ファイルへ複製せず、実際に依存するSkill同士を方向付きBindingで結びます。補助ファイルにはSkillが参照する実資料を登録します。不要なBindingは参照経路を分かりにくくし、循環も作るため、移行元で依存として定義された関係だけを登録します。

## 登録と切り替え

現在の画面にはフォルダー全体を取り込む機能はありません。Asset editorまたはMCP操作で、分類した内容と紐づけを登録します。MCP経由のAIによる変更では、Provenanceに利用者の依頼内容と変更理由を記録します。元ファイルは、AACL側の登録内容と接続を確認するまで保持します。

Runtime入口はAssetの状態とは別に管理します。Claude Code／Codexの設定先を登録して同期すると、Workflowと直接起動を有効にしたSkillの入口が生成されます。直接起動Skillとしての有効状態、Runtime設定先の管理状態、生成ファイルの内容をそれぞれ確認します。Runtime設定先の管理解除後も、生成済み入口は残ります。

移行元の自動読み込み設定は、AACL側の入口から期待したAssetが開き、必要な本文と補助ファイルを取得できることを確認してから利用者が切り替えます。

## 移行後に照合する

- 種類ごとのAsset数と同名Assetを確認し、同名のものは本文と責務を比較する。
- Workflowの工程ごとに担当Roleと完了条件を確認する。
- Skill本文、補助ファイル、Skill間Bindingの向きと参照先を確認する。
- Assetの管理先とSkillの直接起動設定を確認する。
- Runtime設定先、生成された入口ファイル、入口から取得できるCanonical本文を確認する。
- ブラウザーのService接続先と選択中のGlobal／Projectを確認し、移行したAssetの表示を照合する。

MCPのAsset一覧は本文と補助ファイルも返すため、件数や重複の確認と、個別Assetの詳細確認を分けると扱いやすくなります。最後に、移行元の読み込みを切り替えた後のRuntime入口から実際に必要なAssetを取得できることを確認します。
